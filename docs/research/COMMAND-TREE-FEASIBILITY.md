# Feasibility brief: "tree-of-commands + prerequisite/chaining + dynamically-built syntax tree" for the radiology cockpit

## Verdict

**Possible, and closer to "already designed" than to "research."** The idea is, almost line for line, a formalization of structures that already exist in `COMMAND-REGISTRY.md`. The tree-with-prerequisites-and-chaining modeling is a 25-year-shipping pattern (grammar-based command-and-control, HTN/behavior-tree decomposition, task-oriented dialogue). The genuinely new engineering is narrow and build-time, not runtime. The one place the framing is dangerous is the word **"dynamically creates the syntax tree"**: taken literally it pushes toward per-utterance/per-state grammar *recompilation*, which costs seconds and is fatal to the sub-100ms `fire-on-partial` budget. The viable reading — and the one the existing design already implies — is **compile the full tree once at build time; at runtime only gate/swap which leaves are active per `scope`.**

## How it maps onto the existing COMMAND-REGISTRY (most of this is already there)

The user's three nouns map onto already-designed fields:

- **"Tree of all possible commands / hierarchy" → `Scope.parent: CommandId`.** Nested sub-commands are already in the data model (`COMMAND-REGISTRY.md:60`; the doc's own example is "differential diagnose **those**" as a sub-command valid only after findings are selected, `:82-84`). This is structurally identical to SRGS/JSGF `<ruleref>` nesting — "nesting rule-refs IS the tree/hierarchy" (W3C SRGS, https://www.w3.org/TR/speech-grammar/) — and to HTN compound-task decomposition, which is formally isomorphic to a context-free grammar (task=nonterminal, primitive=terminal, method=production; SHOP2, Nau et al. JAIR 2003, https://arxiv.org/pdf/1106.4869). So "syntax tree from finite dependencies" is literally the recognized HTN↔CFG correspondence.
- **"Prerequisite commands / whatnot" → `Scope.requires(ctx) => boolean` and `Scope.mode`.** Already an arbitrary guard (`:60-61`). This is exactly VoiceXML's Form Interpretation Algorithm guard (`cond=` ECMAScript; the FIA visits "the first form item whose guard condition is not satisfied," https://www.w3.org/TR/voicexml20/), Alexa's required-slot/dialogState elicitation, Rasa CALM **Flow Guards**, and the Behavior-Tree **Precondition decorator** (Iovino et al., RAS 2022, https://arxiv.org/pdf/2005.05842). Mature, shipping technique.
- **"Chaining logic" → the clarification FSM + `async` commands + the cost-tiered commit gate.** Already designed (`COMMAND-REGISTRY.md:89-99`, `:101-119`). This is the right home for it, because **every grammar decoder in the field is single-intent-per-utterance** (Rhino infers one intent at the silence endpoint then resets; chaining is an open, unsupported request, Picovoice rhino#159). Chaining is a **state-machine problem, not a grammar one** — the precedents are VoiceXML FIA and Alexa dialogState, and your clarification FSM is precisely that layer.
- **"Dynamically creates the syntax tree" → scope-gated active-set selection.** The registry already says "the matcher only loads in-scope commands, which also shrinks the search space (faster + fewer mis-fires)" (`:80-81`). That matches the literature exactly: per-dialogue-state grammar switching / `kaldi-active-grammar` per-utterance active/inactive toggling (https://github.com/daanzu/kaldi-active-grammar), and contextual-biasing list swaps that cost ~nothing at decode time (Nigmatulina et al., Interspeech 2023 — EntWER 60.5%→52.4% with RTFX 26.062 vs 26.061 with/without biasing, https://arxiv.org/pdf/2306.15685). **Key correction to the user's mental model:** every cheap real-time mechanism is a *swap/gate over pre-compiled artifacts*, never runtime tree synthesis.
- **B4 "one CommandDef → four targets without drift" → already the registry's stated premise.** "One declaration, four consumers" (`:6`): regex/FST + embedding anchors + LLM tool schema + executor binding, plus the open question of generating Rhino YAML too (`:146-147`). Multi-target codegen from one source is shipping precedent: SRGS ships ABNF+XML "semantically equivalent" forms; Jovo compiles one model into Alexa + Dialogflow; Amazon generates the ASR FST and NLU model from the same intents/slots (https://arxiv.org/pdf/1711.00549); XGrammar/LLGuidance/Outlines all accept JSON-Schema OR EBNF/regex into one internal automaton.

**Bottom line on mapping:** the user is describing the system that is already on paper. They are not proposing a new architecture; they are naming the formalism (a typed command tree compiled to recognizers) under which the existing `CommandDef` already sits.

## What is STANDARD/shipping vs what is genuinely NEW

**Standard / shipping (low risk, off-the-shelf patterns):**
- Tree-of-rules → recognition grammar (SRGS/JSGF/Rhino YAML); rule-ref nesting = `scope.parent`.
- Prerequisite guards at the dialog layer (VoiceXML FIA, Alexa, Rasa CALM Flow Guards) = `scope.requires(ctx)`.
- Per-state active-set restriction to cut false-accepts (command-and-control prior art; kaldi-active-grammar).
- Schema→grammar/FST/JSON-tool-schema codegen (XGrammar, LLGuidance, llama.cpp GBNF, Outlines, ToolDec — arXiv:2310.07075).
- One-source→multiple-recognizers codegen (Jovo; Amazon shared ASR-FST/NLU).
- Grammar-constrained decoding for the L3 LLM's *output validity* (guarantees a valid in-tree command JSON; per-token mask cost is negligible, <40–50µs — XGrammar https://blog.mlc.ai/2024/11/22/..., LLGuidance ~2ms startup / ~50µs avg mask).

**Genuinely new / bespoke (this is where the engineering actually is):**
1. **The 4-way co-generator, specifically the {LLM tool schema + embedding anchors} legs.** Co-generating an LLM tool schema *and* embedding anchors from the same source, kept in lockstep with the regex/FST and a Rhino context, has **no shipping precedent** — it is your invention. Jovo/Amazon cover {grammar + FST}; nobody ships the 4-way generator the registry wants.
2. **The fast-tier/slow-tier handoff for tree validity.** The hierarchy/prereq/LLM resolution cannot sit on the fire-on-partial path; only the flattened flat-matcher can. The unsolved part is how a fast-tier leaf hit is validated against the slow tier's current tree state without re-introducing latency or accepting a command the tree would have disallowed.
3. **Auto-chain-vs-prompt per command under medico-legal constraints** (see Risks).

## Concrete build path

1. **Data model (already exists).** Keep `CommandDef` as the single source: `scope.parent` (tree), `scope.requires(ctx)` (prereq), `patterns`/`synonyms`/`anchors`/`slots`. No new shape needed; this is the formalization step.
2. **Build-time codegen, run as ONE step, outputs never hand-edited (the drift discipline Jovo proves works — "project file is source of truth, build folder gitignored").** Emit from each `CommandDef`: (a) regex/FST + Aho-Corasick artifacts for L1; (b) embedded anchors for L2; (c) the LLM tool schema for L3; (d) — if you adopt Rhino — the Rhino YAML context. Add a **golden round-trip CI test**: round-trip every `CommandDef` through all generators and assert the per-mode active-set partition matches across targets.
3. **Tree flatten → per-mode artifacts.** Because `scope.mode` is finite and static, compile **one artifact set per reachable app-mode** at startup. Do NOT synthesize per utterance.
4. **Runtime active-set pruning = a cheap gate/swap.** On mode transition, swap which pre-compiled set is live (pointer/list swap). Apply `scope.requires(ctx)` as a **runtime mask/filter over the active set**, not a recompile. Use LLGuidance/XGrammar-2 *only* on the L3 LLM leg if you need per-state output grammars (single-digit-ms lazy/JIT compile), never on L1/L2.
5. **Prerequisite chaining / FSM in the app layer.** Per `CommandDef`, mark each prerequisite **auto-satisfiable** (silently run establishing command, then resume — the Rasa CALM `call`/return pattern) vs **must-prompt** (clarification FSM). HTN/SHOP2 will *not* synthesize an unmet prerequisite for you; you author the establishing subtask or the dialog policy. Keep this off the partial path entirely.
6. **Decoder integration (the load-bearing latency decision).** Hot path stays as designed: on-device streaming STT → **L1 Aho-Corasick + L2 Model2Vec cosine in parallel** over partials, with the **cost-tiered commit gate** (local-agreement N=1–3 by `confirm` tier). Grammar decoders are *not* on this path. If you adopt Rhino, run it as a **flat leaf-matcher** for common commands in parallel; the tree/prereq logic lives above it.

## The real risks (be explicit)

- **Dynamic-grammar recompile vs sub-100ms `fire-on-partial`.** This is the #1 trap and it is baked into the user's phrasing. A literal per-state HCLG recompile (determinize/eps-removal/minimize) is **seconds**; a Rhino context retrains in the **Picovoice Console (~5–10s, network round-trip)** — both fatal. Even *swapping a loaded Rhino context* is non-zero and unbenchmarked, and there is **no live context-hot-swap API** (you `delete()`+reinit, or run N warm instances in parallel). Architect for "pre-compile everything, gate at runtime." (Kaldi GrammarFst's ~5% decode overhead at -O2 is the only cheap dynamic-stitch option, https://kaldi-asr.org/doc/grammar.html — but it's still not a fire-on-partial mechanism.)
- **Grammar decoders don't fire on partials.** Rhino/SRGS/kaldi-active-grammar are endpoint-then-commit and expose **no streaming partial-intent hypotheses**; kaldi-active-grammar sets the active grammar at *utterance start*, so a command that becomes eligible mid-utterance cannot retroactively enter that utterance's grammar. The fire-on-partial recognizer is your L1/L2 layer over ASR text, not a grammar decoder. (This is already the design; the risk is regressing toward "let a grammar decode the hot path.")
- **Command ambiguity: GCD guarantees VALID, not CORRECT.** Constraining to in-tree commands forbids hallucinations and structurally enforces prerequisites, but does **nothing** to pick the right command among valid ones. Disambiguation still rides entirely on the embedding anchors / LLM and the calibrated `minConfidence` (isotonic/conformal) — exactly the open calibration problem the registry already flags (`:142`). Tie-breaking is `priority` + the clarification prompt.
- **Real-audio false-accepts.** A command grammar "cannot tell the difference between gibberish and well-formed speech outside coverage" (Gorrell, Eurospeech 2003, https://www.isca-archive.org/eurospeech_2003/gorrell03_eurospeech.pdf); naive JSGF→FST graphs falsely accept OOV speech unless you engineer an `<unk>`/garbage phone-loop backoff. Critically, **contextual biasing only boosts, it does not exclude** (sherpa-onnx hotwords, Deepgram keyterms, Google boost) — so reachability must be a **hard gate** (a true constraint grammar/FST or an app-side reject keyed on `scope.requires`), with biasing layered on only as a soft accuracy aid. Real radiology speech has disfluencies/self-corrections that make pure grammars misrecognize. The registry's "tune false-accept first" (`ARCHITECTURE.md:124`) and reachable-only-vs-full measurement on *your* command set is the correct mitigation; there is no published radiology operating point — you must measure.
- **Prerequisite-chaining UX under medico-legal constraints.** This is the sharpest clinical risk. **Auto-running an establishing prerequisite that alters the report is a patient-safety/audit hazard.** "Silently auto-chained an action that changed the report" is exactly what the undo-log/auditability requirement (`RISKS.md:48`, transcript subtraction with undo entry, `COMMAND-REGISTRY.md:124-130`) exists to guard. The default should **bias to prompt/confirm** for any state-changing prerequisite — which directly fights hands-free flow. `confirm: 'always'` on destructive ops (sign/delete/finalize) already encodes this (`:118-119`); the per-command auto-vs-prompt decision is a real design burden, and getting it wrong yields either dangerous silent state changes or nagging prompts.
- **B4 drift seam is worse than file drift — it's expressiveness loss.** The four targets are not equi-expressive. A Rhino slot/choice grammar **cannot encode `scope.requires(ctx)` runtime guards, `scope.parent` recursion, or dynamic slot vocab** (today's worklist names via `SlotDef.source`, which would need a Console retrain). So "one source → four views" degrades to "one source → 3 live CFG-family views (regex/FST, anchors, LLM schema) + 1 lossy offline-trained Rhino projection that silently drops guards, recursion, and dynamic vocab." A lossless single source must be authored at the **least-expressive common denominator** or carry per-target overrides — and per-target overrides are exactly where drift re-enters. The embedding-anchors leg is also non-derivable from the grammar (open-vocab by design), so it stays in sync by codegen discipline only.

## Net recommendation

Build it — it is a formalization of the existing `CommandDef`, and the modeling is field-solved. Spend the engineering budget on (1) the build-time 4-way generator + golden round-trip CI test, (2) keeping "dynamic" = runtime gate/swap over pre-compiled per-mode artifacts (never recompile), (3) treating any grammar decoder (incl. Rhino) as a flat leaf-matcher beside the L1/L2 fire-on-partial path, not on it, and (4) defaulting state-changing prerequisites to prompt/confirm for medico-legal safety. Do not let the word "dynamically" or the phrase "decode against the grammar tree" smuggle a seconds-scale recompile or an endpoint-then-commit decoder onto the sub-100ms hot path.
